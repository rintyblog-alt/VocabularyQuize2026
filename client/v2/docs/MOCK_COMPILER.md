# 試験コンパイラ V2（Quick Mock の生成）

2026-08-04 に画面へ結線した。それまでは `flags.quickMockCompilerV2 = false` で、
ファイルはあるが実行経路に入っていなかった。

```
client/v2/domain/mock-compiler.js      決定論の層（plan / requestsOf / gate / assemble / verify）
client/v2/domain/mock-compile-run.js   実行の層（AI を呼ぶのはここだけ）
client/v2/ui/quick-mock.js             runGenerateV2() / finishGenerateV2()
```

---

## 1. 考え方

**AI は「1 問ぶんの中身」だけを書く。試験の形はコードが決める。**

| 誰が決めるか | 何を |
|---|---|
| コード | 大問の数・設問の数・配点・番号・解答欄・形式の並び |
| AI | 問題文・選択肢・正解・解説・出典 |

配点は Plan の値をそのまま使い、**AI が書いてきた `points` は読まない**。
だから「100 点のはずが 83 点」は、作りとして起こりえない。

## 2. 段階

```
plan()        条件 → ExamPlan（枠と配点をここで確定）
requestsOf()  ExamPlan → QuestionRequest[]（1 回 3 問ぶんの依頼）
  ↓ AI（generateQuestions）
gate()        1 問ずつ受理 / 不受理（理由つき）
assemble()    受理したものだけ → MockSpec
verify()      Plan どおりか（違えば未完成として扱う）
```

空いた枠だけを名指しで頼み直すので、**できている設問は変わらない**。
V1 は 1 問足りないだけで大問ごと作り直していた。

## 3. 資料の量と、抜け道をふさぐこと

サーバは「1 問あたり 120 字」を目安に、依頼ごとに資料の量を見ている
（`assessEvidence` / `INSUFFICIENT_EVIDENCE`）。足りなければ、その依頼はまるごと断られる。

- 断られたら、次の巡は **1 回の依頼を小さくする**。
  実測: 332 字の資料へ 3 問頼むと必要 360 字に届かず毎回断られていたが、
  2 問（240 字）なら通る。
- ただし **小さく刻めば関門は素通りできてしまう。**
  1 問ずつ頼めば、330 字から 30 問を絞り出せる。それは薄い問題の量産であり、
  「資料から出題する」という約束を抜け道で破ることになる。
  そこで、`evidence.maxQuestions`（= 読めた字数 ÷ 1 問あたりの字数）に達したら
  **頼むのをやめる**。足りないぶんは、足りないと言う。

結果には必ず `evidence` が付き、画面は
「資料から読み取れた内容（約 N 字）では、目安で M 問までです」と出す。

## 4. 足りないぶんだけ作り直す

`run({ plan, filled })` に、すでに受理してある設問を渡せる。
渡した枠は二度と頼まないので、**気に入っている設問が別物にならない**。
画面では「検証」タブの **「足りないぶんを作る」** がこれを使う。

## 4-b. 1 問だけ作り直す

仕上げのとき、設問の id は `q1, q2 …` へ振り直される。
そのままでは「この設問はどの枠か」が引けないので、`assemble()` が
**`slotOf`（仕上がった設問の id → 枠の id）** を返す。

問題の編集欄にある **「この問題を作り直す」** はこれを使う。

1. `filled` からその枠だけを消す
2. `run({ plan, filled })` を呼ぶ（＝空いた枠だけが頼み直される）

配点・形式・番号は枠のままなので、**作り直しても試験の形は変わらない**。
ほかの設問にも触らない。

## 5. 実測（2026-08-04・ローカル Qwen3-VL-30B）

資料は約 1,500 字の日本史テキスト。バッチ 3 問・やり直し 2 巡。
`node vqmockv2.cjs`。

| 条件 | 朝いちばん | 中身を直したあと | **解説の言い直しを止めたあと** |
|---|---|---|---|
| 100 点 / 30 問 | 6 問・保存NG（291 秒） | 30 問（743 秒） | **29 問・381 秒（1.95 倍速い）** |
| 100 点 / 20 問 | 6 問・保存NG（228 秒） | 18 問（388 秒） | **18 問・284 秒（1.37 倍）** |
| 50 点 / 10 問 | 2 問・保存NG（149 秒） | 9 問（276 秒） | **8 問・127 秒（2.17 倍）** |
| 330 字で 30 問 | — | 2 問（95 秒） | **2 問・70 秒**。「目安 2 問」と出し、完成とは言わない |

- **満点は 4 / 4 件で指定どおり。**
- **1 問あたり 24.8 秒 → 13.1 秒**（30 問の条件）。
- 速くなったのは 2 つが重なったため。
  ① 解説の言い直しをやめさせて出力が短くなった
  ② 受理できない設問が減り、**やり直しが 2 巡 → 1 巡**になった

直したのは 5 か所。

1. `AI.generateQuestions` が `retrievalQuery` / `includedAttachmentIds` /
   `requireEvidence` を渡していなかった（依頼文の「問1 選択 10点…」がそのまま
   検索語になり、資料と噛み合わなかった）。
2. 資料不足で断られたときに、同じ大きさで投げ直していた。
3. 門が「正誤問題の選択肢 3 つ」を落としていた（直せるのに）。
4. 同じ id・同じ文の選択肢をそのまま入れていた（→ 保存できない）。
5. 短答に選択肢を付けたまま入れていた（→ 正解が空になり保存できない）。

### まだ頼んだ数に届かない理由（20 問で 18・10 問で 9）

- `tf_side_unknown` … 正誤問題の正解が「正しい／誤っている」のどちらか分からない。
  **当てずっぽうで正解を決めない**ので、その枠は空のままにする。
- `no_source` … 資料の該当箇所を示せていない（資料限定のとき）。

どちらも「黙って埋めない」ための欠けである。画面では数と理由を出し、
「足りないぶんを作る」で空いた枠だけを頼み直せる。

### 届かない理由を数えて、直したこと

「23 / 30 問」の残り 7 問がどこで消えたのかを、`rejectReasons` と
`saveErrors` を出して数えた。上位はこの 2 つだった。

| 内訳 | 何が起きていたか | どう直したか |
|---|---|---|
| `choice_count` **14 件** | 正誤問題なのに選択肢が 3〜4 個。門で落としていた | **落とさない。**「正しい／誤っている」の 2 択へそろえ直す。どちら側か分からないときだけ空のままにする（当てずっぽうで正解を決めない） |
| `duplicateChoiceId` / `duplicateChoiceText` / `tooManyCorrect` | 同じ id・同じ文の選択肢が混ざり、正解が両方に当たっていた（→ 保存できない） | 組み立てのときに **id を振り直し、同じ文はまとめ、正解の指し先を付け替える**（`normalizeChoices`） |
| `emptyAnswer`（短答） | 短答なのに選択肢が付いてきて、選択問題として扱われ、正解の当て先が見つからずに空になっていた | **選択肢が要らない形式には選択肢を付けない**（`NEEDS_CHOICES` で判断） |

この 3 つを直したところ、**30 問頼んで 30 問**そろった（それまでは 6 → 23 → 30）。

**直せるものを門で落としてはいけない。** 落とすと、作り直しても同じことが起きるだけで、
頼んだ数にいつまでも届かない。門は「直せないもの」だけを止める。

やり直しは既定 2 巡までなので、そこで止まる。
足りないぶんは画面で正直に出し、押せば作り直せるようにしてある。

## 6. 確かめ方

```bash
node vqmockcompile.cjs   # 決定論の層（47 件・AI 不要）
node vqmockrun.cjs       # 実行の層（46 件・AI 不要。偽の生成器で失敗を再現）
node vqmockv2.cjs        # 実 AI で 4 条件（資料が足りない条件を含む）
node vqmockui.cjs        # 画面（段階・PC 2 カラム・狭い画面の下の操作）
```

`vqmockv2.cjs` の 4 番目は **わざと資料が足りない条件**にしてある。
ここは「作れない」が正解で、黙って埋めたり数を減らしたりしないことを見る。
数字を良く見せるために、この条件を消してはいけない。
