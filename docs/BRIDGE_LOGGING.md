# Bridge の記録

重い処理をたくさん回すようになるので、**後から「何にどれだけかかったか」を追える**ようにした記録の仕組み。

場所: `~/Library/Application Support/VocabuQuiz/Logs/`

| ファイル | 中身 | 1件あたり |
|---|---|---|
| `bridge.log` | 1 依頼 1 行のあらまし（種類・所要・呼出回数・Token・検証結果） | 短い |
| `metrics.jsonl` | **工程ごとの内訳**・モデル呼び出しの明細・順番待ち時間 | 長い |

分けてあるのは、内訳を混ぜると `bridge.log` が読めなくなるから。

---

## 読み方

```bash
node vqload.cjs            # 全期間
node vqload.cjs 24         # 直近 24 時間
node vqload.cjs 24 stages  # 工程ごとの内訳も出す
```

出るもの: 種類ごとの p50 / p95、順番待ちの実績、人ごとの稼働時間、
失敗した依頼がどの工程で落ちたか、モデルの稼働率。

---

## 書かないもの

- 会話の本文
- 添付ファイルの中身・ファイル名
- 認証トークン（Bridge のトークン・Bearer）
- **生の利用者 ID**

利用者は `owner` として **SHA-256 の先頭 8 文字**だけを書く。
「誰の依頼が重いか」をまとめるための鍵であって、匿名化の保証ではない。
生の ID はクライアントから Bridge へは渡るが（127.0.0.1）、**ファイルには一切書かない**。

`node vqmetricslog.cjs` が実際に 1 件流して、上のどれもログに現れないことを毎回確かめる。

---

## 増え続けないようにしてある

`5MB` を超えたら世代を送る。`.log` → `.log.1` → `.log.2` の 2 世代まで。
それより古いものは捨てる。**最大でも 15MB × 2 ファイル**。

---

## 失敗した依頼も残る

以前は成功したときしか記録していなかった。
いまは失敗・中断でも `status` / `code` / `stoppedAt`（どの工程で止まったか）/ `stages` を残す。
重い処理が壊れた理由を後から追うには、むしろこちらが要る。

---

## テスト

```bash
node vqmetricslog.cjs   # 17 件（Bridge が動いていること）
node vqload.cjs         # 読めるかどうかの確認も兼ねる
```

`local-ai/src/` を触ったら **Bridge の再起動が必要**
（`./local-ai/scripts/stop.sh` → `start-open.sh`）。
