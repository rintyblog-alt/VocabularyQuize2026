# Quick Chat の改善記録（2026-07-27）

利用者の指摘から直したものと、その実測。**測っていないことは「未検証」と書く。**

実行: `node vqchat2.cjs`（17件）/ `node vqchatthink.cjs`（思考中の観測）/
`node vqchatfiles.cjs`（添付の実測）/ `node vqchattone.cjs`（話し方の確認）

## 1. 直したもの

### 1-1. 生成中なのにコピー・再生成ボタンが出る

`hidden` を付けても消えなかった。`.acts{display:flex}` のほうが
`[hidden]` の `display:none` より強く、**一度も効いていなかった**（私の実装ミス）。

→ `.acts[hidden]{display:none}` を追加し、ストリーム側（`paintStream`/`finishStream`）でも
本文の有無で直接切り替える。

**実測**: 本文が空なのにボタンが見えていた回 **53サンプル中 0 回**（修正前は出っぱなし）。

### 1-2. 3ファイル添付しても1件しか入らない

原因は入力欄の後始末の順番。

```js
VQF().add(R.fi.files);   /* add() は途中で await する */
R.fi.value = "";         /* ← その最中に FileList を空にしていた */
```

`input.files` は**生きている FileList**。`add()` が最初の `await` で中断している間に
`value = ""` が中身を消すため、**2件目以降が読まれる前に消える**。
検証も通らないので**理由すら出ない**（黙って落ちる）。

→ 先に配列へ写してから空にする。`add()` 側でも入口で写して二重に守る。

**実測（修正後）**

| 試したもの | 結果 |
|---|---|
| 小さいファイル 3件同時 | **3件とも受け入れ** |
| 1.2MB × 1件 | 受け入れ |
| 8MB × 1件 | 受け入れ |
| 5MB × 3件同時 | **3件とも受け入れ** |
| 40MB × 1件（旧上限 25MB 超） | 受け入れ |

> `U.pickAttachments`（プリセット・Quick Mock 側）は元から配列へ写していたため、
> **この不具合は Quick Chat だけ**だった。

### 1-3. 添付が履歴に残らない

「n 番目の発言 ↔ n 回目の送信」で対応づけていたため、
**すでに会話があると番号がずれて**、控えが古い発言に付いていた。

→ 発言そのものの ID で結びつける（`vq.chat.msgfiles.v2`）。
送信時にいったん預かり、新しいユーザー発言が現れたときに紐づける。
ローカルAI・クラウドのどちらの経路でも同じ仕組みで付く。

**実測**: 送信後に入力欄 0 件／履歴に 1 件、**再読み込み後も残る**。
送った発言に付いていることも確認（別の発言に付いていないこと）。

### 1-4. 待ち時間に何も出ない（②③が出てこない）

ローカルAI 接続時は `startThinking()` が呼ばれず、さらに監視処理 2 か所が
`busy()`（**クラウド側の状態しか見ない**）を根拠に `stopThinking()` を即座に呼んでいた。
加えて別のタイマーが `.think__l` を `textContent` で上書きし、波打つ span ごと消していた。

**実測（修正前）**: 12.2秒の待ち時間のうち表示は **135ms だけ**、波アニメは一度も出ず。
**実測（修正後）**: 14ms 〜 3.7秒 表示、`vq-wave` が当たり、
文言は「考えています → 回答案を作成しています → 回答案を点検しています → 1件の指摘を反映しています」と実際の処理に追従。

文言は実イベントから作る（固定文の巡回はしない）。ファイル読み取り中は
「◯件のファイルを読み込んでいます」。

> **外部検索の表示は未検証。** 現在の Quick Chat は外部検索をしないため、
> 検索中の文言が出る経路は一度も動いていない（実装だけある）。

### 1-5. アクティビティ

- ログが一気に出る → 1件ずつ浮かび上がる。まとめて届いた分は **0/90/180/270ms** とずらす
- 印どうしを縦線でつなぐ
- 完了時にタイマーを止め、「完了しました。＋所要時間」で締める
- **巨大なチェックマーク**: `.adone svg` に大きさ指定が無く既定サイズまで膨らんでいた
- **「処理が完了しました」の重複**: 2か所から emit されていた。下の完了表示と同じ意味なので行として出さない
- **ぴょんぴょん跳ねる**: 毎秒 innerHTML を作り直して浮かび上がりが再生されていた → 作り直さず中身だけ更新

### 1-6. 点滅・上へスクロールできない

`renderThread` が毎回 `innerHTML` で全メッセージを作り直していた。
ストリーミング中は毎トークンで DOM 総入れ替えになり、チカチカし、スクロール位置も飛ぶ。

→ キー付きの差分更新。変わった本文だけ差し替える。
**実測**: 連続更新中も既存ノードは保持、上へスクロールした位置（200px）も保持。

### 1-7. 思考レベルの選択パネルが画面外へ潜る

`.composer` に `position:relative` が無く、`.dd(absolute)` の基準が `.main` になっていた。
ずれ幅は `.cwrap` の下パディングと一致。

| | 修正前 | 修正後 |
|---|---|---|
| PC | +14px | +3px |
| モバイル | **+77px**（下部バー64+12） | +3px |

画面外へはみ出さないよう高さを詰めて中でスクロールさせる処理も追加。

### 1-8. 添付の中身が自分の吹き出しに出てしまう

送信時に資料の全文を**発言そのものへ連結**していた。

```js
if (ctx.text) { text = text + ctx.text; }   /* ← これがそのまま画面にも出ていた */
```

そのため、大きな PDF を付けて送ると、自分の吹き出しに本文が丸ごと流れていた。

→ 資料は **AI へ送る文にだけ**足す。画面に出す発言は打った文だけにする。

- **ローカルAI**: そもそも `attachments` として別枠で渡っているので、連結は不要（二重送信だった）
- **クラウド**: 本文へ足す以外に渡す手段が無いので送信時のみ足し、表示では `[添付資料]` 以降を落とす
- 以前の会話に残っている分も、表示時に落とすので出てこない

**実測**（41KB・402行の資料を添付して質問）

| | 結果 |
|---|---|
| 自分の吹き出し | **36字**（打った文だけ）。資料の中身は混ざらない |
| 添付の札 | `verna-naibu.txt` として残る |
| AI の返答 | 資料にしか無い「ザルカンド条約」を**出典（365–402行）付きで回答** |

つまり**画面からは消えたが、AI には届いている**。

### 1-9. 大きな資料を送ると接続が切れる（私が入れた退行）

`maxTextChars` を 800万字へ上げたぶん、ローカル送信が**抽出した全文をそのまま**
Bridge へ渡していた（`extractedText: a.text`）。
その結果リクエストが数十MBになり、**接続ごと切れていた**
（「ローカルAIへの接続が切断されました」）。

→ 送るぶんだけ `maxContextChars`（12万字）に収める。
短い資料から順に配り、余りを大きい資料へ回す（1本が総取りしない）。
削ったときは **「◯件は先頭のみをAIへ渡しました」** とアクティビティに出す（隠さない）。

**実測**（12MB＋6MB＝18MB の資料を添付して送信）

| | 修正前 | 修正後 |
|---|---|---|
| 送信 | 接続が切れる | **54秒で回答**・エラーなし |
| 抽出 | 439万字＋219万字 | 同じ（取り込みは全文） |
| AIへ | 全文（数十MB） | 先頭のみ・通知あり |

### 1-10. 「警告あり」だけで理由が分からない

札には `statusText`（＝「警告あり」）しか出しておらず、
何が起きたのか利用者に伝わっていなかった。

→ 警告の中身をそのまま出す（長い場合は1行で省略、`title` に全文）。
例: **「20ページは画像化されており文字を取得できません（OCR未接続）」**

### 1-11. その他

- ↓（最新へ）ボタンを **PC・モバイルとも入力欄の真上・中央**へ。丸枠でふわっと出し入れ
- チャットを開いたら**常に最下部**を表示（PC・モバイルとも残り 0px）
- 左パネルのプロジェクトアイコンが巨大（`.srow > svg` に大きさ指定が無かった）
- 思考中のスケルトン（骨組み）を削除。波打つ一行だけにした

## 2. 添付できる大きさ

`__vqChatFiles.LIMITS` の一か所で決まる。**Quick Chat・プリセット作成・Quick Mock 共通**。

| 種類 | 1ファイル上限 |
|---|---|
| ドキュメント・PDF・DOCX・テキスト | **512MB**（200万トークンまで） |
| 画像 | **20MB** |
| CSV・TSV | **50MB** |
| ZIP | 512MB |

1メッセージ **40件** / 合計 **1GB** / PDF **2000ページ** まで。

> **未検証**: 512MB のファイルを実際に読ませてはいない。実測したのは 40MB まで。
> それ以上でブラウザが最後まで処理しきれるかは確かめていない。

### 添付できる大きさと、AI が読める量は別

**添付は 512MB まで通る。しかし AI が一度に読めるのは先頭 12万字ぶんだけ。**
モデルの文脈長（32k トークン）で決まるので、ここを上げても読める量は増えない。

実測でも、12MB の資料の**末尾**に置いた固有名詞（ザルカンド条約）は
**答えられなかった**。先頭しか渡っていないため。
このときモデルは作り話をせず「資料には出てきてないですね」と答えた（望ましい挙動）。

- 削ったことは **「◯件は先頭のみをAIへ渡しました」** と画面に出す
- **未実装**: 質問に関係する箇所を選んで渡す仕組み（retrieval）は無い。
  長い資料の後ろのほうを読ませたい場合、いまは該当ページだけを切り出して添付するしかない

### スキャンした PDF（2026-07-27 対応）

文字レイヤの無いページを**画像に起こして、画像が読めるモデルへ渡す**ようにした。
**OCR エンジンは足していない**（新しい依存は無し）。すでに動いている
Qwen3-VL と、既存の画像添付の経路をそのまま使う。

- `pdf.js` でページを描画 → 長辺 2048px・JPEG 品質 0.9 → `kind:"image"` として添付
- 上限 **12ページ / 24MB**（1枚あたり千数百トークン使うため）
- 画面に「◯ページを画像としてAIへ渡しました」と出す

**実測**（文字レイヤの無い2ページのPDFを作って添付）

| | 対応前 | 対応後 |
|---|---|---|
| 抽出した文字 | 0字 | 0字（同じ） |
| AI へ渡るもの | **何も無し** | **2ページを画像として** |
| 回答 | 資料の内容に触れられない | 資料の中身を読んで答える（32秒） |

> **正確さは保証できない。** 実測で「ザルカンド条約」を**「ヴェルカンド条約」**、
> 「839年」を「39年」と読み違えた（JPEG 品質を 0.72→0.9 に上げても同じ）。
> 段落構成や大意はつかめるが、**固有名詞・数字は取り違えることがある**。
> 札にもその旨を出している。**OCR の代わりとして正確さを期待してはいけない。**
>
> 検証に使ったのは 1240×1754 の合成ページ。実際の 300dpi スキャンでの精度は**未検証**。

## 3. 話し方

堅苦しいという指摘から、会話だけ親しみやすくした。

- `CHAT_IDENTITY` / `CHAT_STYLE_RULES` を新設（`local-ai/src/prompts/base.mjs`）
- 使うのは**会話の3役だけ**（main-writer / reviser / synthesizer）
- **問題文・試験・採点は従来のまま**（共有の `STYLE_RULES` は「絵文字は使いません」を維持）

絵文字が出なかった原因は 2 つあった。

1. `stripEmoji()` が**全トークンから絵文字を削除**していた（プロンプトで許可しても一つも届かない）
2. `inspectFormat` が絵文字を不備と判定し「書式の乱れを検出しました」と警告していた
3. `autoFix()` も絵文字を除去していた

→ いずれも**会話経路だけ**解除（`allowEmoji`）。構造化出力（問題・試験）は影響を受けない。

**実測**

> おはよう〜！今日は何から始めようか？😊
> あー、わかるよ〜。特に「試験勉強」って、なんか重くて、やる気出ないよね。。
> あー、鎌倉幕府の終わりって、結構ドラマチックだったよね〜。📜

絵文字 1〜4 個 / 返答、（笑）も出る。書式警告は出なくなった。

## 5. 複数人で使う（2026-07-27 追記）

実行: `node vqqueue.cjs`（29件・AI不使用）/ `node local-ai/tests/gate.test.mjs`（9件）

### 5-0. 先に引き継ぐこと：同時実行数は上げても速くならない

**同時実行数を増やすほど壊れる。** エンジン（llama-server）が1件ずつしか生成
できないので、通す数を増やすと全員がエンジンの前で詰まって共倒れになる。

| 設定 | 5人が軽い質問を同時に投げたとき |
|---|---|
| 同時 2 ＋順番待ち | **5/5 成功・35秒** |
| 同時 5 | 4/5（1人が固まる）・1500秒 |
| 同時 10 | 3/10 |

「5人が快適に使える」を実現しているのは**順番待ちのほう**であって、同時実行数ではない。
`maxConcurrentGenerations` は **2** のまま。重い依頼を5人が同時に投げても
5/5 成功（最長333秒・弾かれゼロ）を実測している。

### 5-1. 順番待ちが入力欄から見えなかった

並んでいること自体は `queue.wait` として届いていたが、画面に出ていたのは
思考中の一行だけで、**何番目なのか・あと何人待てばよいのか**が分からなかった。

→ 入力欄の真上に帯を出す。**Quick Chat・プリセット作成・Quick Mock の3画面共通**。

```
● 順番待ち　2番目 / 5人中              1分20秒待っています
  ▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░
  前の3人が終わりしだい、自動で始まります
```

- 状態は `window.__vqQueue` の1か所。画面側は `<div data-vq-queue></div>` を
  置くだけで、描画はモジュールが行う（**画面が innerHTML を作り直しても消えない**）
- 進捗バーは「並び始めた時点で前に何人いたか」を基準にする。途中で人が増えても
  基準を取り直さないので**バーが戻らない**
- server 側は `running` / `limit` / `people` も送るようにした（`◯人中` を出すため）
- 心拍（15秒ごと）が45秒途切れたら帯を消す。**出しっぱなしにしない**

**実測**: 3画面とも入力欄の真上に出る（座標で確認）。`queue.wait` を1件流すと出て、
待ち以外のイベントが来たら消える。描き直しても残る。心拍が途切れると消える。

### 5-2. 生成中かどうかが、画面を離れると分からなかった

試験づくりは数分かかる。その間ほかの画面へ移ると、動いているのか止まったのかが
分からなかった（画面を閉じた＝止まった、と思われる）。

→ アプリ内の札を出す。**PC は右上・モバイルは上部**（安全領域を避ける）。

- 出るのは**時間のかかる生成だけ**（試験・問題・採点）。ふつうの会話では出さない
- 生成中は経過時間つきで出しっぱなし → 終わると「試験ができました・◯分◯秒かかりました」
  に変わって5秒で消える。失敗・停止も同じ札で伝える
- 押せば消える。**ブラウザの通知（Notification API）は使わない**（許可を求めない）

**実測**: 右上に出る／モバイル幅では上部に横いっぱい／経過時間が進む／
完了で印と文言が変わる／自分で消える。

### 5-3. Quick Mock・プリセットの添付をどうするか（判断済み）

**「残す＋手動クリア」に決めた。**

Quick Chat は送ったら消えてよいが、Quick Mock とプリセット作成は
**同じ資料から大問ごとに何度も生成する**。送信のたびに消すと2回目以降が
資料を失って壊れる。「全部終わったら消す」も、そのあと一部だけ作り直したい
場合に資料が消えていて同じことが起きる。

→ 送っても消さない。消すのは利用者が決める。

- 札に「資料 ◯件（次に作るときも使います）」と出す
- 1件ずつ外す **×** と、**「すべて外す」** を置く
- Quick Mock には**そもそも外す手段が無かった**（× すら無かった）ので、ここで足した
- 一覧は設定の欄と AI の欄の2か所に出るが、**作るのは1か所**（`attachListHtml`）

### 5-4. 上位プランを先に通す

`ConcurrencyGate` を優先度つきにした。数が大きいほど前に入る。

対応表は `local-ai/config/models.json` の `runtime.queuePriorities`。
クライアントは加入中のプラン名（qredit の `planId`）を名乗るだけ。

| プラン | 優先度 |
|---|---|
| ultra / max | 30 |
| pre | 20 |
| edu_pre | 10 |
| free・不明 | 0 |

> **注意**: `ultra` は**まだアプリ側に存在しない**（いまあるのは free / edu_pre / pre）。
> 増えたときにそのまま効くよう、対応表に先に書いてある。

**永久に始まらない人を作らない。** 1人が抜かされてよいのは **3回まで**
（`gate.mjs` の `MAX_SKIPS`）。それを超えたら、上位プランでも追い越せない。
同じ優先度どうしは先着順のまま。

**実測**（`local-ai/tests/gate.test.mjs` 9/9）: 上位が先に始まる／
上位が6人続けて来ても無料の人は4番目より後ろへ行かない／
二重解放で枠が増えない／停止で待ち行列から外れる／何番目かが呼び出し側へ届く。

### 5-5. 検証

| スイート | 結果 |
|---|---|
| `vqqueue`（今回の新規・AI不使用・29項目） | **29 / 29** |
| `local-ai/tests/gate.test.mjs`（今回の新規・9項目） | **9 / 9** |
| `vq2attach` | 7 / 7 |
| `vqregress`（Quick Chat 回帰・実生成あり） | 正常（Console エラー 0・PC / モバイルとも） |
| 単体（model-runner / check-mock） | 4 / 4・6 / 6 |

> **未検証**: プラン優先度の**通しの動作**。`gate.mjs` の並び替えは単体で
> 9/9 通っているが、「Ultra の人が実際に先に始まる」ところまでは**実機で流していない**。
> `server.mjs` と `config/models.json` を変えたので、**Bridge の再起動が必要**。
> 再起動後に、別プランを名乗る2人で同時に投げれば確かめられる。
